# Persona console and local seed catalogue

Status: local preview; not committed, pushed or deployed. Base: `371eeb5` (synced from `ce3558d`).
Branch: `feat/issue-0082-persona-console`.
Related: GitHub [#82](https://github.com/NeverENG/SeekMemory/issues/82), [#83](https://github.com/NeverENG/SeekMemory/issues/83); local ISSUE-0035.

## Problem and result

The existing management tabs make administrators inspect records individually to
understand persona changes and memory relationships. Persona files can already
bootstrap the active persona, but there is no catalogue/install UI.

This change adds a persona-first console with hash navigation, a local fish
illustration, recent content-free run events, persona history/studio, a Canvas
memory map, impression cards, a local persona store and a Dream journal. Existing
memory editing, diagnostics, tasks, lifecycle logs and traces remain accessible.

The store distinguishes bundled seeds, personal blueprints and the separately
planned chat-import workflow. Administrators can preview/install a seed, save a
sanitized current-persona blueprint, import/update/export a local file, or move a
local pack to a recoverable directory. Installation creates a new revision on the
existing persona chain; it creates no Source and calls no model.

## Ownership and boundaries

- `WebRoutes` authenticates and adapts requests; all new endpoints keep method,
  readiness, size and maintenance-busy guards.
- `ManagementService` owns console operations. Bootstrap, existing update and rollback
  remain the management persona Artifact write paths. There is no new service hub.
- Pure read projections consume `ArtifactStore`; `FilePersonaPacks` implements a
  narrow filesystem port. Services/core do not import storage implementations.
- Graph output is capped at 1,000 nodes and 2,000 edges. Protected nodes retain a
  marker, not text. Detail/evidence access remains an explicit authenticated action.
- Persona install uses the page's expected id/revision and preview content digest. Local pack replacement
  requires the previous pack version; writes publish complete files atomically,
  preserve replaced files, and clean temporary files on failure.
- Export is a blueprint allowlist: text/style/boundaries and provenance metadata.
  It excludes raw Sources, source ids, evidence, ledger, revision history and
  original dialogue corpus when saving the current persona.
- `persona_seeds/` ships two existing authored examples with their declared CC0
  provenance. The original local fish SVG uses the repository's dual license.
  The packer validates tracked manifests, licenses, size, IDs and symlink boundaries.

## Rendering and bundle evidence

Development-only comparison: `dashboard/tools/renderer-spike/README.md` and the
adjacent JSON result. d3-force+Canvas and a minimal WebGL renderer share positions
and dataset. Canvas CPU submission median/P95: 0.7/0.8 ms; WebGL <0.1/0.1 ms;
d3 tick 2.7/3.4 ms (max 14.5 ms). These are CPU timings, not GPU completion or FPS.

Production uses deterministic category clusters with Canvas, not a perpetual
force simulation. Ten zoom redraw samples: 1.0–1.4 ms. Five hundred pure filter
samples: median 0.185 ms, P95 0.218 ms, max 0.278 ms; layout 0.783 ms. The local
acceptance budget is 8 ms drawing / 4 ms pure filtering. This avoids additional
production libraries and WebGL picking/context-loss complexity at the bounded
1k/2k size. The prototype does not claim a complete WebGL library evaluation.

Same-machine production build comparison against `ce3558d`:

|---|---:|---:|
| JS, minified / gzip | 511.03 / 158.78 kB | 556.19 / 172.85 kB |
| CSS, minified / gzip | 62.68 / 10.82 kB | 74.62 / 13.54 kB |

The >500 kB chunk warning exists on the base and remains. No production dependency
was added. Mock fixtures, renderer spike and development draw measurements are
excluded from the release bundle. Canvas allocation in one production-preview
viewport was 3.33 MB; the comparison page's WebGL vertex buffers were 40 KB. These
are different resources, not total heap/GPU memory measurements.

## Risks, current limits and rollback

- True host acceptance is outstanding: load the packaged plugin in a faithful
  AstrBot staging container and test auth, bridge calls, file permissions and
  installation/revision refresh. No permission to deploy production was requested.
- Graph and impression **responses** are bounded; the current repository read API
  still enumerates artifacts before projection. Very large databases need a
  separately profiled repository pagination change. UI search/filter works on the
  current bounded snapshot/page and says so.
- Local pack updates assume one plugin process owns its data directory; manual
  concurrent filesystem editing is outside the version check. Removed/replaced
  packs live under `persona_packs/.trash` and are not auto-purged.
- The console consumes the upstream rollback API with a diff, reason and confirmation. Chat import (#76)
  is clearly unavailable; favorability (#77) has no nav entry. Missing historic
  Dream triage metrics show “未记录”. The UI shows the configured daily time,
  not a fabricated next-run timestamp.
- Persona evolution is shown through revisions, not invented graph vertices or
  relationship scores. Current corpus quality rules remain owned by core.
- Revert this feature commit/merge to restore the old console; no database schema
  migration is introduced. Keep the plugin data directory. Reverting code does
  not undo persona revisions intentionally installed by an administrator.
